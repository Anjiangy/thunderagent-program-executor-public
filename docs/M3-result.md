# M3 结果：program 亲和到底值多少

日期：2026-10-23　机器：`<ascend-host>`（Ascend 910B2 × 2，device 0/1）
链路：`client → controller :9000 → executor :8100 → vLLM :8022 | :8023`

## 问题

M2 只证明了"能跑通、账本自洽"。M3 问的是：**把 program 钉在同一张卡上，到底赚不赚**。

## 方法：同一条链，只扳一个开关

| | A 臂 | B 臂 |
| --- | --- | --- |
| controller | 同一个（节流、容量账本完全一致） | 同一个 |
| executor | 同一个 | 同一个 |
| **placement** | `affinity`——program 首轮落在哪就一直在哪 | `roundrobin`——每个请求轮流换卡 |

`EXECUTOR_PLACEMENT` 是唯一变量。其余全部相同：prompt、并发、种子、模型、max_tokens。
每臂用**互不相同的程序前缀**（arm 标签进前缀），所以 B 臂不可能继承 A 臂的缓存。
所有测量点都压在 controller 的节流阈值以下（集群容量 228352 token），否则测到的就是
"节流"而不是"亲和"。

负载形状（模仿 agent）：每个 program 有自己的长前缀（= 它自己的系统提示/仓库上下文），
然后逐轮把工具输出追加进上下文，共 6 轮。这正是 prefix cache 能吃到的形状。

## 结果（2500 词前缀 × 6 轮，单卡 114176 token）

| 并发 program | 亲和命中率 | 轮询命中率 | 亲和 turns/min | 轮询 turns/min | 亲和 p50 | 轮询 p50 |
| --- | --- | --- | --- | --- | --- | --- |
| 16 | 89.5% | 83.3% | 417 | 381 | 1.90s | 1.91s |
| 32 | **81.3%** | **60.1%** | **556** | **351** | **1.96s** | **4.78s** |
| 40 | **85.5%** | **53.0%** | **704** | **372** | **1.95s** | **6.15s** |

原始数据：`data/m3_affinity.csv`；图：`data/m3_affinity.png`（`scripts/plot_m3.py` 可重画）。

## 为什么是"剂量-反应"关系

每个 program 的上下文约 **4600 token**（= 442338 / 96）。单卡 KV 容量是 **114176 token**。

- **N=16**：轮询时每张卡要装下全部 16 个 program = **73.7K < 114K**，装得下，
  所以两张卡都不驱逐，命中率和亲和几乎一样（83% vs 90%，差的那点就是首轮冷启动）。
- **N=32**：轮询时每卡要装 **147K > 114K** → 开始驱逐 → 命中率掉到 60%。
  亲和时每卡只装 16 个 = 73.7K → 装得下 → 81%。
- **N=40**：轮询每卡 **184K**，超出 61% → 命中率跌到 53%。亲和每卡 92K → 稳在 85%。

**这就是 M3 真正想说的话**：亲和不是"永远有用"，它是**容量压力下的保险**。
working set 装得下一张卡时它几乎不产生收益（N=16 两臂打平），一旦装不下，
它守住的命中率和吞吐差距随压力单调放大。

## 附带观察

- 吞吐差距从 N=16 的 1.09× 拉到 N=40 的 **1.89×**；p50 从持平拉到 **3.2×** 慢。
- 轮询臂的 p50 随 N 上升（1.91 → 4.78 → 6.15s）——驱逐导致的重算直接变成用户等待。
- 亲和臂 p50 基本不动（1.90 → 1.96 → 1.95s），说明它把"重算"这个变量按住了。
- p95 比 p50 高很多（9s 级）：因为首轮所有 program 同时冷启动、长 prefill 撞在一起。
  这不是亲和的收益项，是负载形状的固有成本。

## 一次失败但有用的实验

N=48 的轮询臂跑到 16 分钟超时。检查现场：controller 里 `paused=3`，vLLM 两张卡
`running=0 / waiting=0`。

原因不是死锁，是**两种机制叠在一起**：48 × 4600 ≈ 221K 已经贴住 228K 的集群容量，
controller 开始暂停 program；而轮询又让每卡要装 221K（远超 114K）导致极端重算。
暂停 + 重算互相拖，单个请求等过 900 秒。

这件事的价值：它标出了**干净对照的上界**——要把 N 压在 40 以内才能只测亲和。
同时也说明下一阶段（亲和 + 节流 + 迁移叠加）真正要打的硬仗在 N≈48 之后，
那里才是 Fig5 那种"命中率崩到个位数"的区间。

## 这个实验证明了什么 / 没证明什么

**证明了**：
1. 亲和本身有效，且收益随 KV 压力单调增长（命中率 +21~32pp，吞吐 1.6~1.9×）。
2. 收益出现的条件可以被容量算术预测（每卡 working set 是否 > 114K），不是玄学。
3. executor 的 pin 真的作用到了 vLLM 的前缀缓存上（不是只改了张表）。

**没证明**：
1. **KV 迁移的价值**。本实验 `mode=recompute`，一次迁移都没发生；迁移在 M4。
2. **真 agent 负载**。这里用的是同形状的合成负载（长前缀 + 逐轮增长），
   mini-swe-agent 的真实步进还没接上来。
3. **大规模下的行为**。N>40 只有一次失败的观测，没有可用数字。
4. 绝对数字不能和 Fig5 的论文曲线直接比：模型（Qwen2.5-14B）、卡（910B2）、
   并发规模都不同，能比的是**趋势和相对倍数**。

## 复现

```bash
# 每一臂：重启 executor（指定 placement）+ 重启 controller（清空 program 表）
<server-dir>_run.sh affinity   a40 40 6 2500
<server-dir>_run.sh roundrobin b40 40 6 2500
```

`scripts/plot_m3.py` 读 `data/m3_affinity.csv` 出图，不依赖 GPU。

# 汇报问答集：路线甲（ThunderAgent 本体 + program 级放置/搬运）

> 用途：把过去一周真正被问到、以及汇报现场最可能被问到的问题，连同答案和证据放在一起。
> 每个回答都尽量落到数字和产物路径上；没有数据的就直说"没测"。

---

## 0. 一页结论

**做了什么**：在 2×昇腾 910B2 上把"ThunderAgent 的 program 准入 + 我们自己的 program 级放置/搬运"跑成真机系统，并用 90+ 次实验测它的边界。

**三条立得住的结论**

1. program 亲和是有效的：裸 ThunderAgent 内部，亲和 vs 轮询 = 76.10% vs 44.58%（+31.5 pt）。
2. 预热式交接能让"迁移后第一轮"从 0 命中变成 96.8~97.3% 命中。
3. 跨卡 KV 搬运在昇腾上物理可行：首 token 0.228 s → 0.118 s（1.82×）。

**三条不成立的主张**

1. 没有一档赢过裸 ThunderAgent（唯一可比档 81.59% vs 81.11%）。
2. 搬家在常规负载下不触发；触发了也多为负收益（TA 在环：65.4% → 61.9%）。
3. 真·近无损块级迁移在本平台做不到（三条通道全部卡在契约层）。

**下一步一句话**：把"放置信号"从 pin 个数换成字节预算，并在"34/40 钉卡 + 总需求 0.9 容量"这一格上重测搬家。

## 1. 方向类

### Q1 我们要解决的问题到底是什么？

**答**：多轮 agent 任务的 KV 局部性。一个 agent 任务（我们叫 program）会把同一段长上下文反复送进模型，每次都带工具调用的空窗。如果这张卡留着它的前缀缓存，第 2 轮之后基本全命中；如果被放到另一张卡，就得整段重算。

**所以问题不是"怎么调度请求"，而是"怎么让一个 program 的轮次尽量落回它缓存所在的那张卡"**，以及"实在落不回去时，是重算划算还是把块搬过去划算"。

### Q2 为什么是"ThunderAgent 本体 + 嵌入 Llumnix 思想"，而不是反过来？

**答**：因为准入和放置是两层正交的东西，而 ThunderAgent 已经把准入做好了（容量记账 + 暂停/恢复 + 死锁保护），Llumnix 的强项是放置与迁移。我们缺的是后者，所以把它挂在 ThunderAgent 后面，而不是把 ThunderAgent 塞进 Llumnix 的 GlobalScheduler。

还有一个现实理由：Llumnix v0 钉在 vLLM 0.6.3.post1（v0 引擎/CUDA/NCCL），本机是 vLLM 0.23（v1 引擎/NPU）。直接搬 Llumnix 的调度器要改的东西比自研一层还多。

### Q3 路线甲和路线乙是什么关系？乙还要不要做？

**答**：同骨架、约 90% 复用——同一张 program 表、同一个集群 `/metrics`、同一个 `_do_migrate` 接口，差别只在"搬"的执行体：甲 = 目标卡重放一次 prefill（recompute handoff），乙 = 真的把 KV 块搬过去。

乙不是白做，但不该现在做：**甲的实验已经证明"搬家这条路的收益上限很低"**，在没有正收益之前投入 C++/HCCL 是错的顺序。

## 2. 机制类（现场最可能被追问的）

### Q4【核心】均衡负载之后吞吐不应该更大吗？为什么 TA + 迁移反而效果不尽如人意？

**答**：因为"均衡"解决的不是这里的瓶颈。分四层说：

1. **吞吐由"每轮要算多少 token"决定，而 prompt 重算只是其中一部分**。agent 每轮还要生成输出、还要等工具（docker 跑测试）。我们的负载里 15 s 空窗是"等工具"，这段时间 GPU 本来就在服务别的 program——搬家省下的那点 prefill 时间，摊到整轮墙钟里只有百分之几。
2. **搬一次是有固定代价的**。我们的搬运要两段：源卡跑一次 `do_remote_decode` 的 prefill 拿握手包（capture ≈0.13 s），目标卡再把块读过来（pull ≈0.14 s）。合计 ≈0.27 s，比它省下的 ≈0.09 s 还多。所以单次搬家是净亏，只有"这一搬能救回后面很多轮"才划算。
3. **多数跑次里两张卡本来就均衡**。实测 `usage = {'a': 0.562, 'b': 0.540}`，差值 0.02，远低于 `gap ≥ 0.10` 的触发线。没有"一热一冷"，搬家就没有作用对象——这不是策略保守，是没有活干。
4. **超容时搬家更没用**。工作集一旦超过单卡容量，源卡的块本来就在被不断驱逐，capture 抓到的握手包可能指向已回收的块；搬过去也命中不了几次，代价照付。实测超容档：transfer 43.5% vs recompute 51.2%，p50 0.71 vs 0.47 s。

**一句话**：均衡提升的是"缓存驻留质量"，而吞吐瓶颈在"每轮的计算量与工具等待"；当均衡本身不成立（要么已均衡、要么装不下）时，搬家既无收益还要付代价。

**证据**：`docs/M5-pd-spike.md`、`docs/M6-total-table.md`、`docs/M8-B-correction.md`、`data/m8_b_migration.csv`。

### Q5 program 亲和为什么有效？值多少？

**答**：因为前缀缓存是按"块"存的，同一个 program 的下一轮请求带的是"上一轮上下文 + 新观察"，前缀完全一致，所以能命中。换张卡就命中不了。

**剂量反应**（N 个 program × 6 轮，2500 词前缀）：

| 并发 | 亲和 | 轮询 |
|---|---|---|
| 16 | 89.5% | 83.3% |
| 32 | 81.3% | 60.1% |
| 40 | 85.5% | 53.0% |

关键是 N=16 时两者打平（每卡都装得下），N=32 开始亲和明显占优——**亲和是容量压力下的保险，不是恒收益**。

**证据**：`data/m3_affinity.csv`、`data/m3_affinity.png`、`docs/M3-result.md`。

### Q6 搬家什么时候触发？为什么你们跑出来 0 次？

**答**：四个条件必须同时满足：`hot ≥ 0.75`、`cold ≤ 0.55`、`gap ≥ 0.10`、候选 program 的 `in_flight == 0`（且非迁移中、有 prompt_body、体积能塞进冷卡剩余）。

0 次的原因有两类，必须分清：

- **没有对象**：两卡需求比接近 1（0.562/0.540），本来就均衡；
- **有对象但被正确挡住**：差值小于 gap，动手反而会破坏局部性。

我们曾经把第二种误判成"阈值太严"，后来加了 `[bal]` 打印才发现真相——这也是我们把它写进方法学坑的原因。

### Q7 我们的迁移和 Llumnix 的"近无损"差在哪？

**答**：差在"搬的是什么"。Llumnix 搬的是 KV 块本身（CUDA/NCCL 上的 block copy，SoA），中断时间是块传输时间；我们搬的是"重新算一遍"（目标卡重放 prefill），代价是一次 prefill 的算力与时间。

| | Llumnix | 我们（甲） |
|---|---|---|
| 搬什么 | KV 块 | 不算，重放 |
| 中断 | 块传输 | 一次 prefill（0.1~0.3 s） |
| 前提 | 有 P2P/存储通道 | 只需目标卡能跑 |
| 收益条件 | 卡还有余量、只是不均 | 不搬就要反复整段重算 |

**结论**：我们做的是"迁移语义的近似"，不是"近无损迁移"。这个区别在汇报里必须说清楚，否则会被追问"你们的迁移开销是多少"而答不上来。

### Q8 那三条"真迁移"通道为什么都不通？

**答**：三条各自卡在不同契约上：

- **Mooncake store**：元数据通了（`lookup_exists_total_keys` 有值、`Keys` 增长），但读侧永远 miss。根因是写侧块哈希不是内容寻址（同一 prompt 两次跑哈希不同），读侧无法复现。
- **LMCache**：vLLM 0.23 的 `LMCacheConnectorV1` 需要打过补丁的 LMCache（`device_ops`），PyPI 上最新 0.5.6 也没有这个符号。
- **Offloading**：`offloading/worker.py:81` 断言 `isinstance(layer_kv_cache, torch.Tensor)` 失败——昇腾的 KV cache 不是裸 tensor，是布局契约不兼容。

**共同点**：都不是"性能不够"，而是"接口对不上"。这也解释了为什么我们最后选 p2p（`MooncakeConnectorV1`）——它是唯一在 NPU 上真跑通的通道。

## 3. 数据类

### Q9 1.82× 是不是等于"提速 82%"？

**答**：不是。它只覆盖"一次 turn 的首 token"，且是最优条件（源卡 KV 是热的、无排队、单请求）。同一实验里，端到端把 capture+pull 算进去约 0.27 s，比省下的 0.09 s 还多。

准确说法：**在"这段 KV 已算好且已在另一张卡"的前提下，读过来比自己重算快 1.8 倍；但让这个前提成立的代价与收益基本相抵。**

### Q10 为什么短查询（40 词）我们输给 TA 26.7 pt？

**答**：输在放置信号，不输在载体。

| 模式 | 命中率 |
|---|---|
| 裸 TA，亲和 | 76.10% |
| 裸 TA，轮询 | 44.58% |
| 我们，pin | 49.40% |
| 我们，开搬家 | 43.34% |

裸 TA 自己内部"亲和 vs 轮询"差 31.5 pt，说明亲和的价值是真的；我们的 pin 只有 49.40%，接近它的轮询水位——因为我们的排序键是"钉住的 program 个数"，它算的是"每个 program 要多少 KV"。40 词时 program 大小差异被放大，pin 计数完全看不出来。

### Q11 N=40 时你们"停住"，TA 却能跑完，是不是 bug？

**答**：当时是 bug，现在已修。根因是 controller 用**聚合口径**（把所有 program 的上下文加总跟集群容量比），而实际放置是 per-card 的；再加上"暂停不释放簿记"，导致 `paused=24 / total=0` 的假死。

修法是在 `_scheduled_check` 里加进展保证：如果等待队列非空但没有任何 program 真正挂在后端上，就强制恢复一个。修完 72/72 全成功，p95 0.34 s。

**但要诚实**：修好之后在 229K 容量下 N=40 仍然跑不完（40×4.6K≈184K 接近容量），这是容量问题不是调度问题。

### Q12 85.7% 和 18.6% 这两个数怎么理解？

**答**：它们不是同一档负载。

- 85.7%：40 program × 800 词，每卡需求 0.37 容量 → 装得下，上限 87.5%，实测贴顶；
- 18.6%：40 program × 1500 词 + 70% 重尾×3，总需求 ≈125K+ vs 单卡 114K → 装不下，必然互相驱逐。

我一度把 18.6% 解释成"两卡不均"，后来加 `[bal]` 打印看到 `{'a': 0.562, 'b': 0.540}` 才纠正：**是总量超容，不是不均**。

### Q13 为什么三种容量口径不能混？

**答**：因为我们换过三次引擎配置，单卡容量分别是 114,176（892 块）、47,616（372 块）、约 95K。同一句"命中率 40%"在不同口径下含义完全不同。所以 `docs/EXPERIMENTS.md` 每组标题都标了口径；跨口径的表格一律不并列。

## 4. 方法学类

### Q14 合成负载可信吗？为什么不用真实 SWE 流量做全量对照？

**答**：合成负载测机制，真实流量测链路，两者都想做但真实流量当时不具备对照条件。

真实 SWE-agent 每步的墙钟由 docker 跑测试决定（30 s~几分钟），还有镜像缺失造成的失败；想在同一台机器上做四模式 × 3 次重复，它给不了这种可控性。所以先用合成负载把"机制值不值"量出来。

真实流量那次跑通了链路（8 实例 73 s，6 个真跑），但 `program_id` 退化成步数（`vllm_model.py:131`：`job_id if job_id>0 else n_calls+1`），每个请求都成了新 program，亲和不存在——所以那 8 行数据不能当 A/B。

**要升级成 A/B，只差两步**：给每个实例传 `job_id`；按本地镜像筛实例。

### Q15 单次跑次够不够？为什么每格要重启引擎？

**答**：不够，而且我们吃过亏。同一配置重复跑，命中率会漂移（39.6% → 18.6% 那次就是引擎状态被子压满所致）。做法是：每格重启引擎、每格 3~4 rep、只报中位数 + 全部散点。

重启的坑也记下来了：只 `pkill vllm.entrypoints` 不够，残留的 `VLLM::EngineCore` 会一直占着 53.6 GB 显存，下一个引擎会报 `Free memory ... 11.53/60.96 GiB`。必须一起杀。

### Q16 你们做过几次自我纠错？会不会还有没发现的错？

**答**：至少三次记录在案：18.6% 误判为不均、fill 以为能造倾斜（实际到 0.85 就溢出）、平衡器"没触发"误判为阈值严（实际是部署的三份代码不同源，缺 `entries()`）。

**风险确实还在**：本仓库有三份副本（本地、`<server-dir>`、`<server-dir>`），补丁只落一份时症状是"机制不生效"。这条已写进方法学坑：真机前先 `md5sum` 比对两端 `executor/*.py`。

## 5. 局限与下一步

### Q17 当前最硬的局限？

**答**：三个。

1. **没有可比档的胜出**。所有"我们 vs 裸 TA"的对比里，最好也只是打平；
2. **搬家没有正收益的场景**（除了人为压到 0.95 容量的急救态）；
3. **没有真块级迁移**，所以"迁移开销"这个话题我们无法给出 Laridae/Llumnix 那种数字。

### Q18 如果只做一件事，做什么？

**答**：把放置信号换成字节预算，并在"34/40 钉卡 + 总需求 0.9 容量"这一格重测搬家。理由是：短查询实验里 26.7 pt 的差距全部来自放置，而 0.9 容量是唯一"既不均、又装得下"的区间。

### Q19 这套东西的价值在哪？

**答**：三个层面。

- **工程**：一套能在昇腾上跑、可复现、能把 program 级放置与搬运拆开测的 harness（90+ 跑次、16 节实验记录）；
- **认知**：把"亲和有效、搬运低效、容量是主因"这三件事用数字钉住，避免后续在错的方向投入；
- **诚实**：我们明确记录了三条"不成立的主张"，也包括三次自己的误判。

# Llumnix 融合实验 · 汇报材料（2026-10-25）

> 一句话结论：**工程上跑通了（program 会被认出来、会被钉在卡上、能在卡之间搬 KV），但性能上没有一档超过裸 ThunderAgent。** 我们缺的不是"搬运"，是"按 program 体积做容量记账的放置决策"。
> 负载换了 SWE-agent 会怎样：**大概率不会让我们赢**，但会抹平搬运的时延代价——文末给出可检验的预测。

---

## 一、先把名词讲清楚

| 名词 | 通俗解释 | 在这套实验里的具体含义 |
|---|---|---|
| **KV cache（KV 缓存）** | 模型读完一段文字后，把"理解结果"存下来，下次遇到同一段文字就不用再算一遍 | 显存取在 NPU 上，每张卡 64 GB，要跟模型权重抢空间 |
| **prefix cache（前缀缓存）** | 上面那件事只对"开头这一段"生效：开头相同，就能直接复用 | vLLM 以 128 token 为一个"块"来存，块内容哈希相同即可复用 |
| **hit rate（命中率）** | 这一轮需要的块里，有多少是缓存里已有的 | 统计口径 = `prefix_cache_hits / prefix_cache_queries`，来自 vLLM 自带 `/metrics` |
| **recompute（重算）** | 没命中的部分只能重新跑一遍前向 | 代价是时间和算力；我们用 `queries − hits` 的 token 数计量 |
| **program（程序实例）** | 一个独立的 agent 会话：读任务 → 想 → 调工具 → 再想 | 我们让每个 program 有自己独立的长前缀，模拟"每个程序上下文不同" |
| **program affinity（亲和）** | 同一个 program 永远发给同一张卡 | 因为它的上下文只在那张卡上有缓存，换卡就要重算 |
| **throttling（限流/节流）** | 卡装不下时，先让一部分 program 停下等，而不是全部挤进去互相驱逐 | ThunderAgent 的做法：暂停一部分 program，等有空间再放行 |
| **eviction（驱逐）** | 缓存满了就把旧块扔掉 | 扔掉的块下次再用就得重算——这正是命中率崩掉的原因 |
| **capacity wall（容量墙）** | 所有 program 的上下文加起来超过卡容量之后，命中率断崖式下跌 | 本轮实验的核心现象，见第二节 |
| **recompute handoff（重算式交接）** | 把 program 挪到另一张卡时，在新卡上把它的前缀重新算一遍 | 等价于"搬家费 = 一次预填充" |
| **transfer handoff（KV 搬运式交接）** | 把 KV 块真的从源卡搬到目标卡（Mooncake p2p） | 好处是不重算，代价是搬运时间和握手 |
| **p50 / p95** | 一半请求快于 p50，95% 请求快于 p95 | 用"轮"（一轮 = 一次 LLM 调用）为单位测 |
| **tpm** | turns per minute，每分钟完成多少轮 | agent 场景里墙钟受工具影响大，只能同条件横比 |

## 二、实验环境与负载

**硬件**：单 pod，2 张昇腾 910B2（每卡 64 GB），`/dev/davinci0`、`/dev/davinci1`。
**模型**：Qwen2.5-14B-Instruct，`--max-model-len 4096`（保持 KV 便宜），`--gpu-memory-utilization 0.60`（把 KV 压到一个够紧的规模，好制造容量墙）。
**每卡 KV 容量**：`372 块 × 128 = 47,616 token`（来自 `vllm:cache_config_info`），两卡合计 **95,232**。

**负载形状（合成，可控）**：

| 参数 | 取值 | 为什么这么设 |
|---|---|---|
| program 数 | 40 | 让"所有 program 的上下文总和"能超过两卡容量 |
| 每个 program 前缀 | 40 / 600 / 900 词三档 | 40 词 ≈120 token（不挤）；600 词 ≈1050 token；900 词 ≈1561 token |
| 轮数 | 8 轮 | 8 轮的理论命中率上限 = 7/8 = 87.5%（第一轮必然 miss） |
| 轮间隔 | 15 s | 模拟 agent"等工具返回"的空窗，也是搬运最不伤人的窗口 |
| 倾斜 | `--skew-frac 0.85` | 把 34/40 个 program 强制钉到 a 卡，制造"热卡" |
| 臂（arm） | 裸 TA / 重算交接 / KV 搬运 | 同一台机器、同一对引擎、同一晚 |

**三个"负载档"的物理含义**（这是看懂结果的关键）：

| 档位 | 热卡上的 KV | 占容量 | 现象 |
|---|---|---|---|
| 不挤（40 词） | ≈2.4k | 0.05 | 谁都装得下，搬家没有意义 |
| 中等（600 词 × 34 个） | 35.7k | 0.75 | 还装得下，但已经接近墙 |
| 超容（900 词 × 34 个） | 53k | **1.11** | 装不下，必然互相驱逐 |

## 三、实验结果（全部同一台 pod、同一晚）

### 3.1 长前缀：三臂对照

| 场景 | 臂 | 命中率 | 重算 token | 吞吐 | p50 | p95 | 搬家次数 |
|---|---|---|---|---|---|---|---|
| 均匀 0.44 | 裸 TA | **81.59%** | **60,408** | 157.6 tpm | 0.363 s | 0.451 s | — |
| 均匀 0.44 | 重算交接 | 81.11% | 61,728 | **159.8 tpm** | **0.340 s** | **0.444 s** | 0 |
| 均匀 0.44 | KV 搬运 | 79.73% | 66,208 | 158.3 tpm | 0.354 s | 0.452 s | 0 |
| 倾斜 0.75 | 重算交接 | 74.11% | 85,848 | 152.4 tpm | 0.365 s | 0.567 s | 5 |
| 倾斜 0.75 | KV 搬运 | **75.24%** | **83,490** | 151.2 tpm | 0.432 s | 0.577 s | 5 |

图：`data/m6_curve.png`（左：命中率 vs 热卡负载；右：p50 vs 同一横轴）。

### 3.2 短查询：四个模式（这一档最能说明"亲和值多少"）

40 词前缀、40 program × 8 轮、15 s 间隔，容量完全够：

| 模式 | 命中率 | 重算 token | 吞吐 | p50 | 搬家 |
|---|---|---|---|---|---|
| 裸 TA · program 亲和 | **76.10%** | **14,976** | 320.2 tpm | **0.748 s** | — |
| 裸 TA · 轮询（对照） | 44.58% | 32,880 | 292.3 tpm | 0.922 s | — |
| 我们 · 亲和（不动） | 49.40% | 34,464 | 306.2 tpm | 0.866 s | 0 |
| 我们 · 亲和 + 平衡器 | 43.34% | 43,948 | 294.6 tpm | 1.251 s | 10 |

**这一档给出两个硬结论**：
1. **亲和本身值 31.5 pt**（裸 TA 从轮询 44.58% → 亲和 76.10%）。
2. **我们的放置不如它**：同样钉卡，我们只 49.40%。差别不在搬运，而在"首轮把 program 放哪张卡"——它按 program 级容量记账，我们只按"钉住了几个"排序。

### 3.3 一句话判读

- 容量不紧时：三臂在噪声内（81.6 / 81.1 / 79.7）。
- 容量接近墙（0.75）：搬运微弱领先（+1.1 pt），但 p50 慢 18%。
- 超容（1.11）：搬运明显更差（−7.7 pt、重算 +20%、p50 慢 50%）——源卡块已被驱逐，搬过去也命中不了，代价照付。
- **结论：搬运救不了拥挤。** 真正有效的是"别让卡超容"（放置 + 准入），而那正是 ThunderAgent 已经在做的事。

## 四、实验中遇到的问题（按"卡住时间"排序）

### 4.1 数据面：KV 块哈希跨进程对不上（最隐蔽）
- 现象：A 卡写入 store 成功（`Keys: 27`），B 卡对同一 prompt 查询 27 个键**命中 0**。
- 根因：vLLM 在 `PYTHONHASHSEED` 未设置时用 `os.urandom(32)` 生成 `NONE_HASH` 参与块哈希，两个进程算出的块 ID 天然不同。
- 修法：所有引擎统一 `PYTHONHASHSEED=0`（实测：不设 → 两次运行哈希不同；设 0 → 完全相同）。**不改算法、不重编 .so。**

### 4.2 连接器角色写错（第二隐蔽）
- 现象：p2p 搬运时 B 侧报 `SocketHandShakePlugin: malformed json` / 180 s 超时。
- 根因：两侧都配成 `kv_both` 时不会启动发送线程，元数据里 `remote_port` 为空。改成 A=`kv_producer`、B=`kv_consumer` 后立刻通。

### 4.3 三条"现成"通道各自的硬伤
- `MooncakeStoreConnector`：元数据通（lookup 能找到键），但数据面 `adxl Connect ... timeout`，且 `put` 常半失败（keys=10 failed=5）。
- `LMCacheConnectorV1`：公版 0.5.6 没有 `device_ops`，`ImportError` 直接起不来。
- `OffloadingConnector`：断言 `isinstance(layer_kv_cache, torch.Tensor)`，NPU 侧 KV 是"两个独立分配"，布局契约不兼容。

### 4.4 平衡器两个我自己的 bug（值得写进复盘）
- 用了不存在的指标键 `kv_capacity_tokens` → `usable` 恒为空 → **平衡器一次都没执行过**，日志一行不打。此前所有"阈值太严"的解释全部作废。
- 修好后改用 `kv_cache_usage_perc` 作信号，但它统计的是**淘汰后**的占用（常年 0.09/0.0）→ 仍然不触发。换成"Σ 已钉住 program 的 prompt_tokens ÷ 容量"才对。

### 4.5 工程杂项（每条都真卡过人）
- 起昇腾引擎必须 source ATB 环境（`source /usr/local/Ascend/nnal/atb/set_env.sh --cxx_abi=1` + 完整 `LD_LIBRARY_PATH`），否则 `OSError: libop_plugin_atb.so`。
- 端口冲突：Ascend 侧 `side_channel_port = kv_port + dp_rank`，两卡都用默认 14579 会撞车，必须给第二张卡换端口。
- 裸 ThunderAgent 的 `--backends` 会被 `app.py` 的 import 顺序冻结成 `localhost:8000`，只能在 import 之前 `set_config`（`ta_launch.py` 就是干这个的）。
- ThunderAgent 路由是**有状态**的：上一次被中断的运行会留下 40 个 paused program，下一次直接继承 → 每跑一次必须重启路由进程。
- 迁移窗口内 executor 返回 503 + `Retry-After`，压测端必须重试，否则记成失败（我们踩过一次 `failures=45`）。

### 4.6 我自己的两次误判（写出来提醒）
- "日志里没有输出 = 没执行"：实际是 `tee` 把 bench stdout 写进另一个文件，我 grep 错了文件，白排查两轮。
- "命中率 0% 一定是测量 bug"：实际是 62k 负载压 47.6k 容量的必然结果，就是容量墙。

## 五、如果负载换成 SWE-agent，会不会有对我们有利的数据？

### 5.1 先看 SWE-agent 的流量形状
一个 SWE-bench 实例跑起来是这样的：
- **开头**：`system prompt` + 工具说明（固定，约 5–8k token，**跨实例共享**）；
- **然后**：`problem_statement`（每个实例不同，几百 token）；
- **再然后**：agent loop，每步"看一眼输出 → 想 → 发一个命令"，每步新增 1–3k token，**累计上下文一路涨**；
- **工具调用之间**：真实耗时几秒到几十秒（跑测试更久）；
- **典型规模**：30+ 步，单实例上下文最终 20–30k token。

### 5.2 用我们已有的数据去推
- 我们的模型/卡配置下，**单卡 47.6k**，单实例涨到 20–30k → **一张卡只装得下 1–2 个活跃实例**。
- SWE-agent 一开就是 20–40 个实例并发 → 每卡需求是容量的 **8–20 倍**。
- 这个数量级上，**亲和已经救不了**（不是"换卡重算"的问题，是"根本装不下"），命中率会被压到个位数到二三十——这正是 ThunderAgent 论文里 vLLM 那条塌掉的曲线。
- 而 ThunderAgent 的 throttling 恰好就是为这个形态设计的：**暂停一部分 program，让活跃集落进容量**。它在 SWE-agent 上会比裸 vLLM 好很多（论文数据 60%+ vs 个位数）。

### 5.3 所以对我们有利吗？
**不利的部分（大概率发生）**：
- 命中率、吞吐的横比，我们仍然输给裸 TA——因为输的是"放置质量"和"多一跳"，而 SWE-agent 只会放大容量墙，不会改变这两个劣势。
- 搬运在超容档已经证明更差；SWE-agent 几乎全程处于超容档。

**可能有利的部分（值得测）**：
- SWE-agent 的**工具空窗是几十秒级**，而我们的 capture+pull 实测 0.27 s。也就是说，在这个负载下**搬运的时延代价会被空窗完全吸收**——"搬运比重算慢 18%/50%"这个结论会消失。
- 如果场景是"**某张卡被 throttling 暂停后腾出空间**"，把一个暂停中的 program 用 KV 搬运挪到那张卡上（而不是重放重算），理论上能省一次 prefill。这是我们唯一还没测过、且 SWE-agent 天然会造出来的窗口。

### 5.4 我的预测（可证伪）
在 SWE-agent 负载、20–40 并发下：
- 裸 vLLM：命中率个位数（容量墙）。
- 裸 TA：命中率 50–70%（throttling 把活跃集压进容量）。
- 我们（两种交接）：**不高于裸 TA**，差距主要来自放置；搬运臂的 p50 劣势会从 18–50% 收敛到 0–5%。
- 也就是说：**SWE-agent 会让"搬运"看起来没那么糟，但不会让"我们"看起来比 TA 好**。

### 5.5 要证伪/证实，最小实验
1. 把 mini-swe-agent 的 20 个真实实例打到我们的 executor 上（`job_id` 直接当 `program_id` 用，已有代码支持）；
2. 同时跑裸 TA 对照；
3. 只看三个数：命中率、单步 p50、以及"暂停时长占墙钟比例"；
4. 若"搬运臂 p50 − 重算臂 p50 < 5%"，则 5.3 的第二条成立，值得继续做"暂停窗口内搬运"；否则路线甲应当收尾，把结论写成"在无 KV 搬运通道的平台上，program 级放置与准入才是有效杠杆"。

## 六、给汇报的一句话总结

> 我们在昇腾平台上把"program 感知 + 跨卡 KV 搬运"整条链路打通并做了可复现的量化，结论是**搬运本身不是瓶颈，放置决策才是**：容量不紧时三种做法打平，接近容量时搬运微弱领先但时延变差，超过容量时搬运明显更差。下一步要么把 program 级容量记账搬进放置（可与 ThunderAgent 正面对比），要么改用 SWE-agent 的真实流量去检验"长工具空窗是否能让搬运变免费"。

# M7：真实 SWE-agent 流量的第一次 A/B（结论：这一档测不出差异）

日期：2026-10-25　拓扑：tm4(mini-swe-agent) --ssh 隧道--> Ascend executor:8100 --> vLLM 8110/8111（集群容量 228,352 token）

## 负载与方法

- 实例：`filter_regex.txt`（93 个 lite 实例，镜像全部预拉）前 28 个，`--slice 0:28`，`--workers 28`；
- 每个实例 5 步（`step_limit: 5`），前缀 2000 词（每 program ≈2.9K token，无跨实例复用）；
- program 身份：`vllm_model.py:131` 的 `program_id = job_id`，而 `swebench.py:301` 把 `instance_number`（=任务计数器 1..N）当 job_id 传下去 → 实测 executor 表里就是 `1..28`；
- 两臂：`EXECUTOR_BALANCE=off` 与 `skew`（hot 0.75 / cold 0.55 / interval 10s / `MIGRATE_CARRIER=transfer`）；
- 每臂跑之前重启 executor，program 表清空；每臂用独立 `MSA_PREFIX_SALT`，避免跨臂缓存复用。

## 结果

| 跑次 | 臂 | 完成 | 墙钟 | 命中率 | 重算 token | 搬家 |
|---|---|---|---|---|---|---|
| 1 | off | 28/28 | 101 s | 80.53% | 156,647 | 0 |
| 2 | off | 28/28 | 180 s | 76.56% | 193,138 | 0 |
| 3 | skew+transfer | 28/28 | 149 s | 76.85% | 187,431 | **0** |

## 判读

1. **同臂跑次差异比两臂差异更大**：off 两次 101 s / 180 s（1.78×），命中率 80.5% / 76.6%。单次对比毫无意义。
2. **搬家一次都没发生**：28 × 2.9K ≈ 81K，只占集群 228K 的 35%，平衡器阈值（单卡 75%）碰不到。也就是说这一档两臂在机制上等价。
3. 结论：**这一档不是"搬运没效果"，而是"搬运没触发"**。要测真实流量下的搬运，必须让 28 个 agent 把单卡压过 75%。

## 压力档的意外发现

把前缀抬到 6000 词（每 program ≈8.7K，28 个 ≈244K > 228K）后：
- 单卡 `kv_cache_usage_perc` 打到 1.0，9 分钟只完成 17/28；
- 同时 **引擎的 `vllm:prefix_cache_queries_total` 变成 2.5e9 这种不可信值**（正常量级 8e5）——那个区间的计数器不能用来算命中率，只能看墙钟/完成数。

## 下一步（已定，不需要再探索）

- 中间档：前缀 4000 词 × 40 实例 ≈ 232K，让单卡过 75% 线；
- 每臂 3 次，主指标用墙钟与完成数，命中率作为参考；
- 判据先写死：中位数墙钟 ≤ 对照，且搬家次数 > 0，才算"搬运在真实流量下有效"。

## 追加：真实流量下平衡器没有天然触发条件（2026-10-26）

| 配置 | 臂 | 完成 | 墙钟 | 搬家 | 备注 |
|---|---|---|---|---|---|
| 6 实例 / 2000 词 | off | 6/6 | 83 s | 0 | 命中 81.5% |
| 6 实例 / 2000 词 | skew | 6/6 | 56 s | 0 | 命中 77.3% |
| 28 实例 / 2000 词 | off | 28/28 | 101 s | 0 | 命中 80.5% |
| 28 实例 / 2000 词 | off(重跑) | 28/28 | 180 s | 0 | 命中 76.6% |
| 28 实例 / 2000 词 | skew | 28/28 | 149 s | **0** | 命中 76.9% |
| 40 实例 / 3000 词 | off | 40/40 | 195 s | 0 | 计数器失真 |
| 40 实例 / 3000 词 | skew | 40/40 | 257 s | **0** | 同上 |

三个成立的事实：

1. **program 身份是真的**：`job_id = 任务计数器`，executor 表里就是 `1..N`，每实例一个 program。
2. **搬运一次都没触发**，包括单卡装到约 77%（40 × 3.9K ≈ 78K/卡 vs 114K）。原因不是阈值，而是**放置天然均衡**：pin-count 放置把 40 个 program 分成 20/20，两卡需求差 < 10%（`gap` 条件不满足）。
3. **压力区计数器不可信**：40×3000 词时引擎 `vllm:prefix_cache_queries_total` 报到 6.6e9、`hits` 9.2e7（正常量级 8e5），据此算的"命中率 9%"是伪值；同区间墙钟与完成数仍可信。

结论：**真实 agent 流量下，迁移不是一个会自己发生的杠杆**——入口放置已经把"两卡不均"抹平了。此前合成实验的 34/40 倾斜是 `/seed` 人为制造的，真实流量没有这个入口。

两条路：A 把放置改成故意不均（填满一卡再溢出），人为制造可被平衡器修复的不均；B 承认真实流量下无触发条件，把迁移定位成"面向外部不均可控场景的能力"。
倾向 B + A 的小规模对照：先按 B 写结论，再用 A 做一次"人为不均 → 平衡器修复 → 收益"的端到端。

## 追加二：故意制造倾斜也没能让平衡器动起来（2026-10-26）

新增 `EXECUTOR_PLACEMENT=fill`（把 program 依次填到第一张卡，直到它的 kv_usage ≥ 0.85 才溢出到第二张），就是为了让真实流量下也出现可被修复的不均。

结果（40 实例 / 2000 词 / 5 步）：

| 臂 | 完成 | 墙钟 | 搬家 | 说明 |
|---|---|---|---|---|
| fill + balance=off | 40/40 | 268 s | 0 | — |
| fill + balance=skew | 40/40 | 269 s | **0** | 平衡器仍未动 |

两个原因：

1. **没到热阈值**：fill 把 40 个 program 大致按 30/10 分到两卡，热卡约 30×2.6K ≈ 78K / 114K = 0.68，低于 `EXECUTOR_BALANCE_HOT=0.75`，`_balance_once` 直接返回。
2. **计量被上一轮污染**：前一轮 40×3000 词把引擎压到满容量后，`vllm:prefix_cache_queries_total` 累积到 6.5e9（正常 8e5），从此该引擎的命中率读数全部失真——除非重启引擎，否则之后任何跑次的命中率都不能用。本轮两个 fill 臂的 `hit_rate` 因此是 0/0，不是真的零命中。

### 要在真实流量里看到搬运，需要同时满足

- 每卡需求 > 0.75 × 114K ≈ 86K：即热卡上 ≥ 33 个 2000 词 program，或 ≥ 22 个 3000 词 program；
- 另一卡显著更空（gap ≥ 0.10）；
- 引擎计数器干净（跑前重启 vLLM）。

这三个条件在当前"40 实例"的批次里凑不齐；真实流量下这是稀疏事件，而不是常态。

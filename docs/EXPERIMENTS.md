# 全部实验总表（单一文档）

> 汇总 2026-10-23 ~ 10-26 在昇腾 910B2 ×2 上做的全部实验。每条包含：条件、数据、对比、分析、产物位置。
> **阅读前提：不同实验的容量口径不同，数字不能跨组并列。** 每组标题上都标了当时的单卡容量。

## 0. 环境与口径

| 项 | 值 |
|---|---|
| 硬件 | Ascend 910B2 × 2（/dev/davinci0、davinci1） |
| 推理栈 | vLLM 0.23.0 + vllm-ascend，Qwen2.5-14B-Instruct |
| 容量口径 A | `--gpu-memory-utilization 0.8 --max-model-len 32768` → 892 块 × 128 = **114,176 token/卡**，集群 228,352 |
| 容量口径 B | `--gpu-memory-utilization 0.6 --max-model-len 4096` → 372 块 × 128 = **47,616 token/卡** |
| 容量口径 C | `--gpu-memory-utilization 0.8 --max-model-len 16384` → ≈ **95,232 token/卡**（近墙实验用） |
| 命中率天花板 | 每个 program T 轮时，首轮必 miss，理论上限 `(T-1)/T`。3 轮 = 66.7%，8 轮 = 87.5% |
| 重算 token | `Σ(prefix_cache_queries_total 差分 − prefix_cache_hits_total 差分)`，取两卡之和 |

## 1. M0 — 可行性探针（口径 A）

**目的**：判断「program 级 KV 迁移」在本平台是否有物理通道。

| 探针 | 问题 | 结果 |
|---|---|---|
| P1 | `KVTransferConfig` 是否可用 | **PASS**，12 个字段齐全，CLI 有 `--kv-transfer-config` |
| P2 | 是否有 connector 实现 | **PASS（结构性）**，vllm-ascend 有 `kv_transfer` 目录与 Mooncake/Nixl 等注册名 |
| P3 | 能否直接用 Llumnix | **FAIL**，Llumnix 钉 vLLM 0.6.3.post1（v0 引擎/CUDA），本平台是 0.23（v1 引擎/NPU） |
| P4 | prefix cache 是否真的生效（迁移收益的前提） | **PASS**：`same-1 dq=13919 dh=0` → `same-16 dh=13824`（99.3% 命中） |

**分析**：P4 是关键——如果 prefix cache 不生效，任何"迁移省重算"的推理都不成立。P3 的失败决定了：不能把 Llumnix 当进程跑，只能把它当"迁移语义的参考实现"。

## 2. M1 — program executor 自身（口径 A）

**条件**：独立仓库 `program-executor`（executor 接两台 vLLM，`/v1/chat/completions` 代理 + program 表 + 集群 `/metrics`）。

| 检查 | 结果 |
|---|---|
| 单元测试 | 10 passed（本机 0.04 s，昇腾 0.07 s） |
| 真机 smoke | 12/12 PASS |
| `/metrics` 聚合 | `vllm:cache_config_info{block_size="128",num_gpu_blocks="1784"}` = 892×2 |
| 亲和 | 同一 program 两次请求都落同一卡；迁移后下一次落新卡 |
| 铺开 | 6 个 program → 两卡各 3；`executor:programs_pinned` 各 3 |
| 与 ThunderAgent 解析器互操作 | 其 `VLLMCacheConfig` 读出 `block_size=128, num_gpu_blocks=1784`、capacity=228352；`prefix_cache` 命中率 0.5208 ⇒ **controller 端零改动** |

**分析**：这一步只证明"能接、能算、能记住落点"，不涉及任何性能主张。

## 3. M2 — 真 controller 串起来（口径 A）

**条件**：client → controller(:9000，钉住 7ddc861 的 ThunderAgent) → executor(:8100) → vLLM(:8022/:8023)。

| 检查 | 结果 |
|---|---|
| 端到端 | 12/12 PASS |
| 容量透传 | controller 读到 1784 块 × 128 = 228,352，与我们聚合值一致 |
| program 身份 | 3 个 program 落成 a/b/a，身份穿过 controller 未被吞掉 |
| 节流探针 | 30 program × 9k token ≈ 270K > 228K ⇒ `peak_paused=11`，30 个请求全 200，24.3 s |

**关键接缝（修掉的真问题）**：ThunderAgent 的 `remove_program_id()` 会把 `extra_body.program_id` 从 body 删除，且 `client.stream()` 不转发 header ⇒ executor 只看到 `default`。修法：给上游注入 `program_id_hint`（不改钉住的文件，SHA256 仍通过）。

**分析**：这一步证明"TA 的准入/暂停"和"我们的放置/搬家"可以共存于一条请求路径；但**共存 ≠ 叠加收益**，见 §9。

## 4. M3 — program 亲和值多少（口径 A，2500 词 × 6 轮）

**条件**：同一链路，唯一变量 `EXECUTOR_PLACEMENT=affinity|roundrobin`；每臂独立前缀避免跨臂污染；测点都在容量内（集群 228K）。

| N | 亲和命中率 | 轮询命中率 | 亲和吞吐 | 轮询吞吐 | 亲和 p50 | 轮询 p50 |
|---|---|---|---|---|---|---|
| 16 | **89.5%** | 83.3% | 417 tpm | 381 tpm | 1.90 s | 1.91 s |
| 32 | **81.3%** | 60.1% | 556 tpm | 351 tpm | 1.96 s | 4.78 s |
| 40 | **85.5%** | 53.0% | 704 tpm | 372 tpm | 1.95 s | 6.15 s |

**机制**：N=16 时轮询每卡 16×4.6K=73.7K < 114K，装得下 → 两臂打平；N=32 每卡 147K > 114K 开始驱逐 → 掉到 60%；N=40 184K → 53%。亲和始终在每卡 92K 以下，稳在 81~86%。

**边界**：N=48 时轮询臂 16 分钟超时（httpx ReadTimeout），现场 controller `paused=3`、vLLM `running=0/waiting=0` —— 呈「卡空着、controller 满着」形态，与我们自己的聚合口径无关（后来在 M6 确认是 TA 的容量判据与可放置性脱钩）。⇒ **干净对照的上界是 N≤40**。

**分析**：亲和的收益不是恒定的，是**容量压力下的保险**：一旦单卡装不下，轮询会把命中率砸到一半以下。

## 5. M4 — mode=kv 的"预热式交接"（口径 A）

**语义澄清**：本平台无可用 KV block 搬运通道（见 §10），所以最初实现的 `mode=kv` 实际是**重放式再物化**：迁移前把该 program 的前缀灌到目标卡做一次 prefill，再挪 pin。

| 检查 | 数字 |
|---|---|
| 预填充是否留缓存 | `same-1 dq=13919 dh=0` → `same-16 dh=13824`（同一 prompt，max_tokens=1 的预填充留下可用前缀缓存） |
| 更长前缀能否命中 | `warm-1 dh=0` → `extend-16 dh=13824`（严格更长也命中） |
| 完整迁移路径 | turn1/2 在 a（4032/4089）→ 迁 b 预热（dq+4089 dh+0）→ turn3 落 b（dq+4145 dh+3968） |
| 对照实验（3 次） | m4c **0.9682** vs 0.000；m4f **0.9695** vs 0.000；m4g **0.9726** vs 0.000 |

**修掉的真 bug**：`record_prompt()` 原本"保留最大 prompt"，而 program 表跨 run 存活、同 program_id 复用 ⇒ warm 重放的是**上一次 run 的旧上下文**（所以出现"warm 自己命中 3840、迁移后 turn 却是 0"的怪象）。改为**最新写入胜出**后三次 PASS。

**分析**：`mode=kv`（重放式）能把"迁移后首轮"从必 miss 变成 ~97% 命中；但代价是**多一次 prefill**，这次 prefill 计入 queries 却不产生 hit。

## 6. M5 — 与裸 ThunderAgent 的头对头（口径 A）

**条件**：N=24/32/40，1200 词前缀，3 轮；裸 TA 用 `ta_launch.py`（绕开 app.py 的 import 顺序 bug），我们走 controller+executor。

| N | 臂 | 完成 | 墙钟 | 吞吐 | 命中率 | p50 |
|---|---|---|---|---|---|---|
| 24 | 裸 TA | 96/96 | ~19 s | 309 tpm | 73.4% | — |
| 24 | 我们 | 96/96 | ~19 s | 307 tpm | 73.3% | — |
| 32 | 裸 TA | 128/128 | 23 s | 331.6 tpm | 73.4% | — |
| 32 | 我们 | 128/128 | 23 s | 331.1 tpm | 73.5% | — |
| 40 | 裸 TA | 160/160 | 51 s | 187.4 tpm | 41.8% | 11.16 s |
| 40 | 我们 | 停住 | >900 s | — | — | — |

**N=40 停住的诊断**：controller `programs=40 / paused=10`，而两台引擎 `running=0 / kv_usage=0`；聚合口径下 3 个重尾 program 被扣在 controller 里、`backend=None`，per_backend total=0。⇒ **不是死锁，是"卡空着、controller 满着"**：TA 的容量判据（单 backend 聚合）与真实可放置性脱钩。

**8 轮档**（N=24，2000 词）两臂：86.59%（归一化 99.0%）/ 353.1 tpm。天花板 (8-1)/8=87.5% ⇒ 已贴顶。

**分析**：在容量内，两边在噪声内打平；一旦贴容量，差异全部来自"谁在过载时还能推进"。

## 7. M6-A — 跨卡 KV 搬运是否物理可行（口径 A）

**条件**：两台引擎分别 `kv_producer` / `kv_consumer` + `MooncakeConnectorV1` + `kv_buffer_device=npu`；一次请求 812 token。

| 指标 | 冷启动（目标卡自己 prefill） | 搬运（目标卡从源卡取） | 加速比 |
|---|---|---|---|
| 首 token（3 次） | 0.228 / 0.197 / 0.196 s | 0.118 / 0.110 / 0.113 s | **1.82×** |

**三条证据**：prefill 日志 `Connected to segment: <pod-ip>:20117`；decode 侧 `prefix_cache_queries=812` 且 `kv_cache_usage=0`（说明它没本地 prefill）；`kv_load_failure_policy=fail` 下请求成功（取不到就会失败）。

**关键死条件**：①角色必须是 `kv_producer`/`kv_consumer`，`kv_both` 不会起 `KVCacheSendingThread`，读侧就永远超时；②`protocol` 必须是 `ascend`（rdma/tcp 在本环境被 `rtsHostRegister` 拒绝）；③`kv_port` 两实例不能相同。

## 8. M6-B — 迁移用真搬运（口径 B，单 program）

**条件**：`EXECUTOR_MIGRATE_CARRIER=transfer`，program 迁到目标卡时注入 `do_remote_prefill` + 源卡握手包。

| 场景 | 迁移后首轮时延 |
|---|---|
| 目标卡冷启动（无预热） | 0.627 s |
| 迁移 + KV 拉取 | **0.453 s**（1.38×） |
| 迁移 + 重算预热 | 0.464 s |

**分析**：单 program 层面，真搬运确实比重算略快（0.453 vs 0.464），但差距只有 2%；真正的差距来自"有没有预热"（0.46 vs 0.63）。

## 9. M6 总表 — 三臂同 pod 同晚（口径 B，47,616/卡）

**条件**：40 program × 8 轮 × 15 s 空窗；前缀 600 词（≈1050 token/program，每卡 21K/47.6K）；裸 TA 经 `ta_launch.py`。

| 场景 | 臂 | 命中率 | 重算 token | 吞吐 | p50 | 搬家 |
|---|---|---|---|---|---|---|
| 均匀 20/20 | 裸 TA | **81.59%** | **60,408** | 157.6 tpm | 0.363 s | — |
| 均匀 20/20 | 重算交接 | 81.11% | 61,728 | 159.8 tpm | 0.340 s | 0 |
| 均匀 20/20 | KV 搬运 | 79.73% | 66,208 | 158.3 tpm | 0.354 s | 0 |
| 倾斜 34/40（0.75） | 重算交接 | 74.11% | 85,848 | 152.4 tpm | 0.365 s | 5 |
| 倾斜 34/40（0.75） | KV 搬运 | 75.24% | 83,490 | 151.2 tpm | 0.432 s | 5 |
| 倾斜 34/40（1.11 超容） | 重算交接 | 51.16% | 246,264 | 136.9 tpm | 0.473 s | 12 |
| 倾斜 34/40（1.11 超容） | KV 搬运 | 43.49% | 295,670 | 131.5 tpm | 0.707 s | 12 |

**分析**：
1. 唯一可比档（均匀）裸 TA 高 1.5~1.9 pt，重算也最少 ⇒ **我们不占优**；
2. 0.75 容量：搬运 +1.1 pt 但 p50 慢 18%（每次搬家付 capture+pull，省下的只是一次 prefill）；
3. 超容（1.11）：搬运 −7.7 pt、重算 +20%、p50 慢 50% —— 源卡块已被驱逐，搬过去也命中不了；
4. 均匀档 `moves=0`：**搬运在这一档根本不触发**。

## 11. M6 压力窗口 — 唯一一次"搬家明显有效"（口径 C，≈95K/卡）

**条件**：40 program × 900 词 × 8 轮 × 25% 重尾；人为把 28/40 钉到同一张卡 → 热卡 **0.95 容量**（已超容、反复驱逐）。

| 臂 | 搬家次数 | 命中率 | 重算 token | p50 |
|---|---|---|---|---|
| 不搬家（同样倾斜） | 0 | **7.38%**（4 跑中位） | 450,780 | 1.46 s |
| 搬家 + KV 搬运 | 13 | 49.98%（2 跑） | 262,588 | 0.49 s |
| 搬家 + 重算 | 13 | **54.39%**（2 跑） | 230,414 | 0.49 s |

**分析**：
1. 这组是"急救"，对照组是"同样的烂放置 + 不搬"；**不能**用它证明"搬家优于正确放置"；
2. **重算载体反而优于 KV 搬运**（54.4 vs 50.0）：每次拉取要 capture + pull 两段代价，重算只付一次目标卡 prefill；
3. TA 不在环。

## 12. M6 短查询四模式（口径 B，40 词/≈120 token）

**条件**：40 program × 8 轮 × 15 s 空窗；所谓"短查询"即 SWE-agent 那种小 prompt。

| 模式 | 命中率 | 重算 token | 吞吐 | p50 | 搬家 |
|---|---|---|---|---|---|
| 裸 TA + 亲和 | **76.10%** | **14,976** | 320.2 tpm | **0.748 s** | — |
| 裸 TA + 轮询 | 44.58% | 32,880 | 292.3 tpm | 0.922 s | — |
| 我们 + 钉卡 | 49.40% | 34,464 | 306.2 tpm | 0.866 s | 0 |
| 我们 + 均衡 | 43.34% | 43,948 | 294.6 tpm | 1.251 s | 10 |

**分析**：
1. **亲和本身值 31.5 pt**（76.10 vs 44.58）——这是"program 亲和有效"最硬的证据；
2. **我们输在放置质量**：我们的钉卡只有 49.40%，比裸 TA 的钉卡低 26.7 pt。差别不在载体，而在"首轮把 program 放哪张卡"（TA 按 program 级容量记账，我们只按 pin 个数排序）；
3. 小前缀下搬家是负的（−6 pt、p50 +44%）——容量不紧时搬一次就是白付一次。

## 13. M7 — 真实 SWE-agent 流量（口径 C）

**条件**：mini-swe-agent 1.14.4（tm4），SWE-bench lite 实例，8 workers，`job_id → program_id`；client → ssh 隧道 → executor(:8100) → 双卡。

| 配置 | 臂 | 完成 | 墙钟 | 搬家 | 命中率 |
|---|---|---|---|---|---|
| 6 实例 / 2000 词 | 关均衡 | 6/6 | 83 s | 0 | 81.5% |
| 6 实例 / 2000 词 | 开均衡 | 6/6 | 56 s | 0 | 77.3% |
| 28 实例 / 2000 词 | 关均衡 | 28/28 | 101 / 180 s | 0 | 80.5 / 76.6% |
| 28 实例 / 2000 词 | 开均衡 | 28/28 | 149 s | 0 | 76.9% |
| 40 实例 / 3000 词 | 关均衡 | 40/40 | 195 s | 0 | 计数器失真 |
| 40 实例 / 3000 词 | 开均衡 | 40/40 | 257 s | 0 | 计数器失真 |
| 40 实例 / 4000 词 | — | 38/40 超时 | 900 s | — | 不可用 |
| 40 实例 / 2000 词（强制 fill） | 关/开 | 40/40 | 268 / 269 s | **0** | 读数被污染 |

**分析**：
1. 真实流量的启动是错开的，2000 词档两卡需求都在 0.4~0.7，**永远不越过 0.75 的搬家线**；我加了 `EXECUTOR_PLACEMENT=fill`（填满一卡才溢出）也只能到 0.68；
2. 3000 词以上会饱和：`prefix_cache_queries_total` 累积到 6.5e9（正常 8e5），此后命中率不可用，**必须重启引擎**；
3. 因此真实流量下**只有 28 实例/2000 词这一档是干净可比**，而它也显示两臂在噪声内、`moves=0`。

## 14. 贯穿所有实验的方法学坑（会重复踩的）

| 坑 | 表现 | 修法 |
|---|---|---|
| 块哈希非内容寻址 | 两个进程算同一 prompt 得到不同 block hash（`NONE_HASH` 随机） | 全链统一 `PYTHONHASHSEED=0` |
| `kv_both` 无发送线程 | 读侧永远超时、`hits=0` | 两侧分别是 `kv_producer` / `kv_consumer` |
| `kv_port` 冲突 | side channel 抢端口 | 每实例不同 `kv_port` |
| 平衡器读错容量键 | `kv_capacity_tokens` 从未被 parse 产出 ⇒ 平衡器"从未执行" | 用 `num_gpu_blocks × block_size` |
| 平衡信号用错 | 用 `kv_usage`（驱逐后归零）⇒ 永远不触发 | 用钉住 program 的 `Σ prompt_tokens ÷ 容量` |
| 天花板被忽略 | 3 轮"两臂都 65%"其实是 (T-1)/T 的顶 | 报告必须给归一化命中率 |
| 计数器污染 | 饱和后累计到 1e9 量级 | 每次跑前重启 vLLM |
| TA 有状态 | 中断的运行留下 pinned/paused program，下次直接继承 | 每次重启路由进程 |
| TA 的 import 顺序 | `--backends` 被冻结成 `localhost:8000` | 用 `ta_launch.py`（先 set_config 再 import app） |

## 15. 结论汇总

1. **program 亲和有效**：短查询档 76.10% vs 轮询 44.58%（+31.5 pt）；长前缀 N=32/40 档亲和 81~86% vs 轮询 53~60%。
2. **我们的放置弱于 TA**：短查询 49.40% vs 76.10%（−26.7 pt）。根因是排序信号用"pin 个数"而不是"字节/KV 预算"。
3. **搬家机制成立但不占优**：唯一明显有效的是"热卡 0.95 的急救"（7.38% → 50~54%）；在容量内它打平或负收益（0.75 档 +1.1 pt 但 p50 +18%；1.11 档 −7.7 pt）。
4. **搬运载体不如重算**：超容档重算 54.39% vs 搬运 49.98%；单 program 层面 0.453 vs 0.464（差距 2%）。
5. **真实 SWE 流量不会自发制造"该搬"的场景**：40 实例×2000 词热卡只到 0.68；要触发需 ≥60 实例×3000 词并重启引擎。
6. **TA 与我们的关系**：TA 管准入/暂停，我们管放置/搬家；在容量内两者叠加无增益，在过载时 TA 的暂停已经兜住了最坏情况，搬家在同一窗口里只多付代价。

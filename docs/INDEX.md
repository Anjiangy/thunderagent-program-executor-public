# 按问题索引

不知道从哪读起时，用这张表按"我现在想知道什么"跳。

## 我想知道"这东西到底解决什么问题"

读 `../README.md` 前三节。一句话：让同一个 program 的多轮请求留在同一张卡上，别让前缀缓存白算。

## 我想亲手把它跑起来

`../README.md` 的「真机怎么跑起来」一节，六条环境变量 + 三个 curl。先确认 `/metrics` 里的 `num_gpu_blocks` 是单卡的两倍——这一步不对，后面全错。

## 我想知道"亲和到底值多少"

`M3-result.md`。里面有 16/32/40 三个并发的完整数据、每卡占用推算，以及"为什么 N=16 两臂打平"的解释。

## 我想知道"迁移是不是真的有用"

`M4-result.md`。`mode=kv` 三次跑 96.8/97.0/97.3%，对照组 0%。同一份文档里也写了这次踩到的真 bug：`record_prompt` 原本"保留最大的 prompt"，跨 run 复用 program_id 时会 warm 到上一次的旧上下文。

## 我想知道"跟别人比怎么样"

`M4-compare-plan.md` 是**先写死的判据**（哪个方向算达标），`M4-compare-result.md` 是实测结果。结果本身是"持平"，其中 N=40 那档"我们停住"后来查清是缺陷不是能力，见下一条。

## 我想知道"为什么会停住 / 死锁"

这一条不在 docs 里，在 `../README.md` 的坑第 3 条和 `M4-compare-result.md` 的结尾。根因：暂停的 program 没有任何恢复进展保证，出现"卡空着、controller 满着"。修法是给 `_scheduled_check` 加一行"队列非空且没有任何 program 挂在后端上 → 强制恢复最早的"。

## 我想知道"最新的实验做到哪了"

`data/` 里的 csv 就是原始记录，时间顺序大致是：`m3_affinity.csv` → `m4_kv_results.csv` → `compare/*.json` → `m5_admission.csv` → `m5_heavy4x.csv` → `m5_ceiling.csv`。

`m5_ceiling.csv` 是最后一条、也最重要的一条：**命中率上限是 `(T-1)/T`**。3 轮 66.7%、8 轮 87.5%。所以凡是 3 轮跑出来的"两臂都是 65%"，不是"没差别"，而是"已经在天花板上，测不出差别"。

## 哪些结论已经被后来的实验推翻

诚实起见，列在这里：

| 旧结论 | 出处 | 现在怎么看 |
|---|---|---|
| "per-card 拓扑（每卡一个 executor）也能做迁移" | `step1-percard-status.md` | **不成立**。每个 executor 只认识一张卡，它的平衡循环永远没有对象，`balance_moves` 恒为 0。要迁移必须回到单 executor 聚合双卡 |
| "N=40 我们停住 = 容量到顶、比不过 TA" | `M4-compare-result.md` | **部分推翻**。停住是缺陷（无恢复进展保证），修完后同一负载 72/72 成功 |
| "加 token 体积排序能提升命中率" | 未写进文档，只在对话里 | **不成立**。4× 重尾下两臂 64.3/65.6 vs 63.2/65.2，噪声级差异 |
| "50% 重尾能拉开差距" | 对话里 | **未验证**。两次尝试都在开局死锁，死锁修好后尚未重跑这一档 |

## 还有哪些硬骨头

- 真正搬 KV block（现在只是重放 prefill）；
- turns ≥ 8 且并发真正超过单卡容量时，两臂的定量对比（这是唯一能证明迁移价值的场景）；
- 真 agent 负载（现在是合成负载）。

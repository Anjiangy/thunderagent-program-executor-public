# Llumnix 融合实验 · 详细汇报（2026-10-25 夜）

> 结论先行：**"把工作换个地方"这件事，只有发生在"卡快要满、另一张卡还有余量"的那一小段才值钱；过了墙再搬，等于白付搬运费。** 我们在昇腾上把整条链路（program 识别 → 放置 → 跨卡 KV 搬运 → 平衡器）打通并量化，三种载体全部测过。

## 1. 名词速查（给不做这一行的读者）

| 名词 | 一句话解释 |
|---|---|
| **KV cache** | 模型读完一段文字后存下的"理解结果"，复用就不用重算 |
| **prefix cache** | 只对"开头相同"的部分复用；vLLM 按 128 token 一块，块内容哈希相同即可命中 |
| **命中率 / hit rate** | 这一轮需要的块里有多少已在缓存中（`prefix_cache_hits_total ÷ prefix_cache_queries_total`） |
| **重算 / recompute** | 没命中的前缀只能重新做一次前向，代价是时间 |
| **program** | 一个 agent 会话（读任务→想→调工具→再想），上下文逐轮变长 |
| **affinity（亲和）** | 同一个 program 固定发到同一张卡，因为它自己的上下文只在那张卡上有缓存 |
| **eviction（驱逐）** | 卡装满了就把旧块扔掉；扔掉的块下次用就得重算 |
| **容量墙（capacity wall）** | 所有 program 上下文总和超过卡容量后，命中率断崖下跌 |
| **throttling / pause** | 装不下时先让一部分 program 停下等，而不是全挤进去互相驱逐 |
| **recompute handoff** | 换卡时在新卡把前缀重新 prefill 一遍（"搬家费 = 一次预填充"） |
| **KV transfer / pull** | 通过 Mooncake p2p 把 KV 块真的从源卡搬到目标卡（"搬家费 = 带宽 + 握手"） |
| **p50 / p95** | 一半/95% 的请求快于这个时延，单位是"一轮"（一次 LLM 调用） |

## 2. 硬件与负载

| 项 | 值 |
|---|---|
| 硬件 | 单 pod，2 × 昇腾 910B2（每卡 64 GB） |
| 模型 | Qwen2.5-14B-Instruct |
| 引擎 | vLLM 0.23 + vllm-ascend；A=vLLM:8110（`kv_producer`），B=vLLM:8111（`kv_consumer`） |
| 容量（旧配置） | `--max-model-len 4096 --gpu-memory-utilization 0.6` → **372 块 × 128 = 47,616 token/卡**，两卡 95,232 |
| 容量（新配置，今晚复测） | `--max-model-len 16384 --gpu-memory-utilization 0.8` → 约 **892 块/卡 ≈ 114k token/卡** |
| 负载形状 | 40 program × 8 轮 × 15 s 空窗（模拟等工具），每 program 独立前缀（避免跨 program 共享缓存把命中率抬高） |
| 三档前缀 | 40 词（≈120 token）/ 600 词（≈1050）/ 900 词（≈1561） |
| 倾斜 | `--skew-frac 0.85~0.92`：用 `/v1/programs/{pid}/seed` 强制把多数 program 钉到 a 卡，制造"热卡" |
| 臂 | 裸 TA / 我们·重算交接 / 我们·KV 搬运 / 我们·关平衡器 |

**为什么要人为制造倾斜**：真实 agent 集群里，负载永远是不均的；均匀铺卡时"搬家"根本没有触发条件，测不出任何东西（我们验证过：均匀档 `moves=0`）。

## 3. 五个问题的直接回答

### 3.1 把 `--max-model-len` 调大，能让重算更贵、迁移更划算吗？

**结论：调 flag 本身不改变成本结构；真正起作用的是"实际前缀长度"。**

- `max-model-len` 只是"允许的最大序列长度"，它不改变**每 token 的 KV 大小**（由模型结构决定：Qwen2.5-14B 约 **192 KB/token**，与 900 词 ≈1561 token ≈ 300 MB 的实测吻合），也不改变**卡能装多少**（由 `gpu-memory-utilization` 和权重占用决定块数）。
- 我今晚确实重启到了 `max-model-len 16384 + util 0.8`，容量从 47.6k/卡升到 ~114k/卡。这只让"更长的上下文跑得起来"。
- 真正的"让重算变贵"是**把每个 program 的前缀做长**。我用单 program 做了成本曲线（a 卡预热握手 → b 卡首次 token 时延，`max_tokens=1`）：

| 前缀实际 token | b 卡冷启动（重算） | 从 a 卡拉 KV | 比值 |
|---|---|---|---|
| 286 | 0.108 s | 0.122 s | **0.89×（拉更慢）** |
| 700 | 0.114→0.116 s | 0.125→0.127 s | **0.91×（拉更慢）** |
| 1250 | 0.174 s | 0.134 s | **1.30×（拉更快）** |

- 读法：**拐点在"一千 token 出头"**。再往上拉，pull 的优势会继续扩大（它线性于字节；重算线性于 token×算力），但有个硬约束：114k 的卡里 10k token 的 program 只能放 ~10 个，20 个并发就又过墙——容量墙会先出现，收益还是被吃掉。
- 所以答案是：**能，但只在"每个 program 的上下文几万 token、且并发不高"的组合里成立**，而那正好不是 agent 集群的常态。

### 3.2 这个配置下和原版 TA 对比过吗？

**部分对比过，且结论不利。**

- 有效对比（同一 pod、同一对引擎、同一晚）：

| 场景 | 裸 TA | 我们·重算 | 我们·搬运 |
|---|---|---|---|
| 长前缀 600 词 · 均匀 | **81.59%** | 81.11% | 79.73% |
| 短查询 40 词 · 各自最优 | **76.10%**（亲和）/ 44.58%（轮询） | 49.40% | — |

- **未对比**的部分要写清楚：`max-model-len 16384` 这个新配置下我只做了单 program 的成本曲线，**没有**重跑 40-program 三臂对比（时间不够）。所以"长上下文下谁更强"目前只有成本侧证据，没有端到端证据。
- 为什么我们输：不是搬运不行，是**放置不行**。裸 TA 自己的轮询→亲和是 44.6%→76.1%（+31.5 pt），说明亲和本身极值钱；但我们同样钉卡只有 49.4%，因为它的放置按"每个 program 要吃多少 KV"记账，我们只按"这张卡钉住了几个 program"排序。

### 3.3 "两卡不均衡但都没暂停"的场景会有吗？那时 KV 迁移行吗？

**会有，而且是 TA 的常态；但那时迁移不划算。**

为什么会有：
- TA 的放置以 program 为粒度做容量记账，而它的 token 估算是 **chars/5 的近似**，不是真实 token；
- program 的上下文还会一轮轮长大，估计值会漂移；
- 只要两张卡各自的估算总量都没超容量，它就**不会 pause**——于是完全可能出现"a 卡 34 个轻 program、b 卡 6 个重 program"这种**数量平衡、体积失衡**的形态。

迁移行不行：
- 技术上能搬（我们已经在 0.75 档搬了 5 次，100% 成功）；
- 但收益几乎为零：**没有驱逐压力时，搬家省不到任何东西**。实测 0.75 档：命中 +1.1 pt，p50 反而慢 18%（0.365 → 0.432 s）。
- 真正划算的是"**将要过墙**"那一小段（0.85–0.95）。我们把阈值提前到 0.80 测了一组：

| 组（热卡 ≈0.95） | 命中率 | 重算 token | p50 | 搬家 |
|---|---|---|---|---|
| 关平衡器（4 次） | **7.38%** | 450,780 | 1.46 s | 0 |
| 平衡器 + KV 搬运（2 次） | 49.98% | 262,588 | 0.49 s | 13 |
| 平衡器 + 重算交接（2 次） | **54.39%** | **230,414** | 0.49 s | 13 |

→ **"提前搬"值 43 个百分点**；但同样 13 次搬家，"真搬运"仍输给"重算交接" 4.4 pt（原因：pull 自身计入 queries 不产生 hits；且热卡接近满时源块可能已驱逐，只能拉到一部分）。

### 3.4 TA 的 pause 是把 KV 挪走，还是丢掉重算？

**都不是：它只是"扣住请求"，KV 的处理完全交给 vLLM。**

- 机制：controller 判定容量不足时返回 `HoldDecision`（对客户端表现为等待/`503`），**请求根本没进 vLLM**；
- 于是那张卡上的旧 KV **留在原地**，由 vLLM 自己的 LRU 决定去留（有新请求进来就可能被驱逐）；
- 恢复时把请求重新发出去：块还在 → 命中；已被驱逐 → 重算。
- 一句话：**TA 的 pause 是"时间换容量"，它既不搬 KV，也不主动丢 KV，但也不为 KV 的存活做任何保证。**
- 这解释了为什么"pause 之后命中率会掉"——不是 pause 造成的，是 pause 期间**别的 program 把它的块挤掉了**。

### 3.5 我们是不是"类 TA + KV 搬迁"？触发条件是什么？

**不是。准确的描述是：TA 管"准入与暂停"，我们管"放置与偶发搬家"，KV 搬迁只是可替换的载体。**

拓扑：

```
client ──▶ controller(:9000, ThunderAgent 薄适配器, 未改语义)
               │  ← 这里做 program 级容量节流（pause/hold），与我们无关
               ▼
          executor(:8100, 我们的层)
               │  ← program 表 / 放置(亲和) / 平衡器 / 两种载体
               ▼
        vLLM A(:8110)  vLLM B(:8111)
```

触发条件（executor 的平衡器，全部是显式阈值）：

| 条件 | 默认/实测值 | 说明 |
|---|---|---|
| `EXECUTOR_BALANCE` | `skew` / `off` | 总开关；我们做对比时靠它切臂 |
| 检查周期 | `INTERVAL=2/6/10 s` | 每个 tick 最多处理一次 |
| 热卡判据 | `HOT=0.80~0.90` | 热卡"已钉 program 的 prompt_tokens 之和 ÷ 容量" |
| 冷卡判据 | `COLD=0.50~0.55` | 冷卡必须明显有余量，否则搬了也白搬 |
| 候选 | `in_flight==0` 且有 `prompt_body` | 只能在"空窗"搬，不能搬正在跑的 |
| 每 tick 上限 | `BALANCE_BURST=4` | 防止一次搬太多把机器打满 |
| 载体 | `EXECUTOR_MIGRATE_CARRIER=transfer|recompute` | 默认 recompute；transfer 失败可 `FALLBACK=recompute` |
| 搬运窗口 | 该 program 收到 `503 + Retry-After` | 客户端必须重试，否则记失败 |

关键点：**触发信号不是 vLLM 的 `kv_cache_usage_perc`**。那个值统计的是"驱逐之后"的占用，长期偏低（我们踩过：0.09/0.0，平衡器永远不触发）。我们用的是"已派驻的 token 体积 ÷ 容量"——这是"未来的需求"，不是"当下的占用"。

## 5. 一路上真正卡住人的问题（按隐蔽程度）

1. **块哈希跨进程不一致**：`PYTHONHASHSEED` 未设置时 vLLM 用 `os.urandom(32)` 生成哈希种子，两个进程对同一段文字算出不同块 ID——写进 store 也读不出来。修法：所有引擎统一 `PYTHONHASHSEED=0`（不改算法、不重编 .so）。
2. **连接器角色写错**：两侧都配 `kv_both` 时不会启动发送线程，握手必然超时。改成 A=`kv_producer`、B=`kv_consumer` 立刻通。
3. **三条"现成"通道各有硬伤**：store 数据面握手超时且 `put` 半失败；LMCache 公版 0.5.6 缺 `device_ops`；offloading 断言 KV 必须是 `torch.Tensor`（昇腾侧不是）。
4. **平衡器两个我自己的 bug**：用了不存在的键（从未执行）；用"驱逐后占用率"当信号（永远偏低）。两次都导致"看起来没反应"。
5. **裸 TA 有状态**：上一次被中断的运行会留下 40 个 paused program，下一次直接继承 → 每跑一次必须重启路由进程；它的 `--backends` 还会被 `app.py` 的 import 顺序冻结成 `localhost:8000`（要用 `ta_launch.py` 先 `set_config` 再 import）。
6. **我自己的两次误判**：把"日志没输出"当卡死（其实 `tee` 到了另一个文件）；把"命中率 0%"当测量 bug（其实是容量墙的必然结果）。

## 6. 如果换成 SWE-agent 负载

- **不利的一半**：SWE-agent 单实例上下文会长到 20–30k token。旧配置（47.6k/卡）一张卡只装 1–2 个实例，20–40 并发时每卡需求是容量的 8–20 倍 → 必然深过容量墙。这时 TA 的 pause 主导局面，我们的搬运没有余量可用。**横比命中率我们不会赢**——我们输的是放置质量与多一跳，SWE-agent 不会改变这两点。
- **可能有利的一半**：SWE-agent 的工具空窗是几十秒级，而我们一次 capture+pull 只要 0.27 s。也就是说，**在 SWE-agent 里搬运的时延代价会被空窗完全吸收**；再叠加"热卡将过 0.85 就提前搬"的策略，理论上能拿到我们在 0.95 档测到的同级别收益（7.4% → 50%）。
- **可证伪预测**：SWE-agent、20–40 并发下，裸 vLLM 命中率个位数；裸 TA 50–70%；我们**不高于**裸 TA，但搬运臂的 p50 劣势会从 18–50% 收敛到 0–5%。
- **最小验证**：把 mini-swe-agent 的 20 个实例打到 executor（`job_id` 直接当 `program_id`，代码已支持），同时跑裸 TA 对照，只看三个数：命中率、单步 p50、暂停时长占墙钟比例。

## 7. 边界与未验证

- 所有"近墙窗口"数据每组只有 2–4 次跑；`forced_to_a` 实测 18（bench 钉卡逻辑有上限），热卡 0.95 是"推定值 + 反证（关平衡器只有 7.4% 命中）"，不是直接读到的。
- `max-model-len 16384` 下只做了单 program 成本曲线，**没有**端到端三臂对比。
- 真 KV 搬运只在 p2p（MooncakeConnectorV1）上跑通；store / LMCache / offloading 三条都不通（原因见第 5 节）。
- 绝对数字不可与论文或另一台 pod 的数并列（模型、卡数、容量都不同）。

---

## 8. 下一步建议（按性价比）

1. **把"按 token 体积记账"搬进放置决策**（`best_instance` 的排序键从"钉住几个"换成"已派驻 token ÷ 容量"），这是唯一能解释 49.4% vs 76.1% 差距的地方，改造成本约半天。
2. **把平衡窗口做在工具空窗里**：program 返回 `acting`（等工具）时，若热卡 >0.85 就搬它——这是 SWE-agent 唯一能兑现收益的时机。
3. 用 SWE-agent 真实流量验证上面两条；若"搬运臂 p50 − 重算臂 p50 < 5%"成立，则路线甲可以继续；否则应当收尾，把结论写成"在无 KV 搬运通道的平台上，program 级放置与准入才是有效杠杆"。
